# tiny-symphony 0.2.0: spec

Status: draft 2026-11-12, one review round, waits for the owner. Builds on 0.1.0 (`docs/spec.md`
at tag `v0.1.0`). Process across the tracker, the daemon, git and GitHub: `docs/process.md`.
Research: `docs/research/T-704-github-pr-flow.md`.

## Goal

0.1.0 is a supervisor that owns the pipeline: its own status table, a result file, checks before it
writes to Backlog.md. 0.2.0 turns it into a connector for tix: the tracker owns the statuses and the
gates, the agent works with the tracker itself, the daemon only finds tagged tasks in the watched
statuses, runs agents and says when something went wrong.

## Expected result

- `tiny-symphony run` against tix runs `agent:<name>` tasks from the statuses in `watch`.
- The agent takes the task, writes its notes, opens the PR, puts the link into `external` and hands
  the task over to `handoff_status`; on success the daemon writes nothing.
- The daemon writes only a note, a move to `blocked_status` or a move back to `reopen_status`.
- A central config and an optional project config, like a user and a project `CLAUDE.md`.
- PR watch and cleanup are modules with an on and off switch.

## Philosophy

1. **One job.** Find tagged tasks in the watched statuses, run an agent on each in its own worktree,
   report failures. Not a tracker, not a pipeline, not a merge bot.
2. **Each system owns its state.** Task and status: tracker. Branch: git. PR, CI, merge: GitHub.
   The daemon keeps nothing durable except the attempts file in the worktree.
3. **The agent works like a person.** Same CLI, same rules files, same tracker commands as an
   interactive session. The daemon adds the worktree, the actor name and a short prompt.
4. **Humans gate in the tracker.** A gate is a status the daemon does not watch.
5. **Modules are independent and can be turned off.** Dispatch is the core; the rest are switches.
6. **Small and boring.** One binary, stdlib first, no database, no HTTP.

## Tracker interface

One Go interface, one adapter per tracker. 0.2.0 ships tix only. The adapter runs `tix` with the
working directory `workspace_root`, which is outside any git repository, so `tix list` is not
narrowed to the project of the current folder; the store comes from `TIX_HOME` or the tix default.

| Method | tix command | Used by |
| --- | --- | --- |
| `List(statuses)` | `tix list --status <s> --json`, once per status | dispatch, watch, cleanup |
| `Get(id)` | `tix show <id> --json` | before every write, after a run, reconcile |
| `Repos()` | `tix projects` (text: name, path, count; `-` is no path) | dispatch: the repository of a project |
| `Note(id, text)` | `tix note <id> --as <actor> -- <text>` | every daemon write starts with a note |
| `Block(id, reason)` | `tix move <id> <blocked_status> -m <reason> --as <actor>` | after `max_attempts` |
| `Reopen(id)` | `tix move <id> <reopen_status> --as <actor>` | a run left the task taken; a PR did not land |

`tix move` takes `-m` only into blocked and closed, so the reason of `Reopen` goes into the note
before it. Moving out of in_progress drops the claim, so no separate release is needed.

Task fields the daemon reads: `id`, `title`, `project`, `status`, `tags`, `claim`, `external`,
`rank`, `created`, and the `After: T-N` lines of the body. Statuses are compared trimmed and
lowercased. With tix 0.9 statuses are names with a kind (T-702); the daemon takes names from its
config and needs no kind.

## Actor

Each run has the actor `tiny-symphony:<agent>:<T-N>`. tix takes `--as` before the agent's own
session variables (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`), so the prompt gives the agent this
name for every `tix` command. A claim with this name is ours; any other live claim belongs to
someone else. The daemon writes with `--as tiny-symphony`, so its own writes are told apart from
the agent's in the tix history.

## Run

1. **Collect.** Tasks in the `watch` statuses with a tag `agent:<name>` of a known agent, no live
   claim, not tagged `epic`, every `After:` task closed, a project with a repository. Order: rank,
   then oldest, then id.
2. **Dispatch** while fewer than `max_agents` runs go and the task is not running or in backoff.
3. **Worktree** on `T-<N>-<slug>` from the project repo, found by id and reused across runs.
4. **Agent** in the worktree, own process group, log in `.tiny-symphony/`, pid file, prompt from the
   template (Prompt).
5. **Reconcile** every tick: a run whose task lost its `agent:` tag is stopped (SIGTERM to the
   group, SIGKILL after 10 s), no attempt counted. Status moves during the run do not stop it: the
   agent moves the task itself.
6. **Outcome.** After exit the daemon reads the task again. The tracker state decides, not the
   exit code:

| Task after the run | Outcome | Daemon writes |
| --- | --- | --- |
| left the watched statuses and in_progress (handed over, blocked, closed), whoever moved it | success, attempts reset | nothing |
| in a watched status | failed attempt | nothing |
| in_progress with our claim | failed attempt | note with the reason, `Reopen` |
| in_progress with no live claim (empty or expired) | failed attempt | note, `Reopen` |
| in_progress with another live claim | failed attempt | one note "left in_progress by <claim>; the agent may have missed `--as`"; no move |
| tag removed | run was stopped, no attempt | nothing |

Failed attempts retry after 1, 5 and 15 minutes; the reason (exit code, timeout, "task left taken")
goes into the next prompt. After `max_attempts` the daemon writes a note with the reason and the log
path, calls `Block`, and resets the count, so a human who moves the task back gets a fresh limit.
Attempts and reopens live in `.tiny-symphony/attempts` in the worktree; a deleted file resets them
(known residual risk, as in 0.1.0).

**Every daemon write is guarded.** Right before `Note`, `Block` or `Reopen` the daemon calls
`Get` and writes only if the task is still where the daemon expects it: in a watched status, or
in_progress with our claim, or (for the watch) closed with the same `external`. Anything else means
a human moved it, and the daemon writes nothing.

On start the daemon takes the lock of `workspace_root` and kills leftover agents found by their pid
files (S8 of 0.1.0).

## Prompt

One built-in template for every status, strict (`text/template`, `missingkey=error`). Variables:
`id`, `title`, `branch`, `worktree`, `actor`, `handoff_status`, `attempt`, `last_error`. The text
says: run every `tix` command with `--as {{.actor}}`; take the task; read it with `tix show`; work
only in this worktree, not in the project path that `tix take` prints; put the PR link into
`external`; hand over with `tix move {{.id}} {{.handoff_status}}`, not `tix done`. Project
specifics come from the agent's own rules files and `prompt_append`. The task text is not copied
into the prompt: the agent reads the latest version and the human's comments from the tracker.

## Config

Two layers.

1. Central: `~/.config/tiny-symphony/config.toml`. Everything below.
2. Project, optional: `.tiny-symphony.toml` in the main checkout of the project (the path from
   `tix projects`), read from disk at each dispatch. It may set only `prompt_append` (added after
   the central one), `max_attempts` and `run_timeout_minutes`. Any other key, or a file that does
   not parse, is a failed attempt with the reason in the note at `Block`, so backoff and
   `max_attempts` bound it like any other failure. Agent commands never come from a
   repository: an agent could change them in a PR and the daemon runs outside any sandbox.

```toml
tracker = "tix"
workspace_root = "~/.local/share/tiny-symphony/work"   # must not be inside a git repository
watch = ["open"]              # statuses where agents pick work up
handoff_status = "blocked"    # where the agent puts a finished task (tix 0.9: a review status)
blocked_status = "blocked"    # where the daemon moves a task after max_attempts
reopen_status = "open"        # where the daemon returns a task; must be in watch
poll_seconds = 30
max_agents = 2
run_timeout_minutes = 60
max_attempts = 3
prompt_append = ""

[agents.claude]
cmd = ["claude", "-p", "--permission-mode", "auto", "{prompt}"]
[agents.codex]                # the sandbox must let the agent write the tracker store
cmd = ["codex", "exec", "--sandbox", "workspace-write", "--add-dir", "~/tasks", "{prompt}"]

[watch_pr]
enabled = false
poll_minutes = 5
max_reopens = 2               # PRs that did not land, per task, before the daemon stops reopening

[cleanup]
enabled = true
log_days = 14
```

## Modules

| Module | What | Switch |
| --- | --- | --- |
| dispatch | Collect, dispatch, reconcile, outcome, retries, lock | always on |
| PR watch | every `poll_minutes`, for each closed task with a worktree, no running run and a PR link in `external`: `gh pr view --json state,mergedAt,mergeStateStatus,statusCheckRollup`. Merged: note "merged <sha>", the task is done for the watch. A failed check (`FAILURE`, `ERROR`, `TIMED_OUT`; pending and neutral are not failures) or `mergeStateStatus` `DIRTY`: note with the reason, `Reopen`, reopens + 1. Closed unmerged: note once. At `max_reopens`: one note "PR does not land, needs a human" (marked in the attempts file), no more reopens. A `gh` error: log line, next round | `[watch_pr] enabled` |
| cleanup | for each closed task with no running run: remove its worktree (`git worktree remove`, which refuses a dirty tree), `git branch -d` (refuses an unmerged branch, so a squashed branch stays); logs older than `log_days`. With the watch on it waits until the watch has seen the PR merged or closed, or the task has no PR link | `[cleanup] enabled` |
| check | config, tracker, agents on PATH, repos, `gh` when the watch is on; prints the merged config per project | command |

The watch never switches auto-merge on and never merges (`docs/process.md`, Merge). A task leaves
the watch when its worktree is removed, so the list stays short.

`check` fails when: `watch` is empty or names a status tix refuses; `watch` contains
`handoff_status` or `blocked_status` (every handover would count as a failure); `reopen_status` is
not in `watch`; `workspace_root` is inside a git repository; a project path has a space.

## Boundaries

- R1 an agent starts only inside `workspace_root`, cwd is the task's worktree.
- R2 a task without an `agent:<name>` tag is never touched.
- R5 no shell between the daemon and the agent.
- R6 one daemon per `workspace_root`.
- R7 the daemon never merges, pushes, or deletes an unmerged branch.
- R8 the daemon's tracker writes are only `Note`, `Block` and `Reopen`, each after a guarding `Get`.
- R9 agent commands come only from the central config.

R3 and R4 of 0.1.0 (pipeline transitions, checked result) go away with the result file.

## What goes away from 0.1.0

The pipeline table and `checkResult`; `result.json` and the agent contract; three prompts by status;
the Backlog.md adapter; `[projects]` in the config (the tracker knows the repository); the Review
checks of S6 (clean tree, pushed branch, PR, `verify`): the agent runs the project checks, CI and
the human review do the rest. Kept: worktree per task, lock, leftover agents, backoff, attempts
file, `check`.

## Decisions

- D4 The agent writes the tracker itself. Was D3 (the daemon is the only writer). Reason: the owner,
  12.11: «это чуть ли не основная фича tix что агент сам работает с трекером». Cost: a sandboxed
  agent needs write access to the tracker store (`--add-dir ~/tasks` for codex); the daemon no
  longer checks the result, only where the task ended up.
- D5 The tracker is an interface; tix is the first and only adapter in 0.2.0.
- D6 Success is read from the tracker after the run, not from a result file or the exit code.
- D7 The project config cannot name commands (R9).

## Acceptance

Tests use the real `tix` binary on a temporary store (`TIX_HOME`), a fake agent script and a fake
`gh` on PATH. "The daemon writes nothing" is checked in the store's git log by the actor.

1. Happy path: a task with `agent:claude` in `open`; the fake agent takes it with the given actor,
   sets `external` and moves it to `handoff_status`. The run is a success, no commit by
   `tiny-symphony`.
2. The fake agent exits 0 without moving the task: failed attempt, retry after backoff; after
   `max_attempts` a note and blocked by `tiny-symphony`, and the count is reset.
3. The fake agent takes the task and crashes: note, task back to `reopen_status`, retried.
4. The fake agent hands over and exits 1: success.
5. A human (another actor) moves the task between the run's end and the daemon's write: the daemon
   writes nothing.
6. The tag is removed during a run: the agent is stopped, no attempt.
7. A project `.tiny-symphony.toml` adds to the prompt; one with `[agents.x]` fails the dispatch.
8. Watch on, fake `gh`: merged gives a note and the worktree removed; a failed check gives a note
   and `Reopen`, until `max_reopens`, then exactly one note over several rounds; pending gives
   nothing; `gh` failing gives a log line and no tracker write. Watch off: `gh` is never called.
9. `tix` missing or failing: the tick is skipped, runs go on.
10. `check` fails on each case of the Modules list.
11. One live run per supported agent (claude, codex, kimi) on a throwaway repo: the claim in the
    store carries `tiny-symphony:<agent>:<T-N>`; the owner reads the log.
12. `make ci-check` green; R1, R2, R5-R9 each have a test.
