# tiny-symphony 0.2.0: spec

Status: draft 2026-11-12, waits for the owner. Builds on 0.1.0 (`docs/spec.md` at tag `v0.1.0`).
Process across the tracker, the daemon, git and GitHub: `docs/process.md`. Research:
`docs/research/T-704-github-pr-flow.md`.

## Goal

0.1.0 is a supervisor that owns the pipeline: its own status table, a result file, checks before it
writes to Backlog.md. 0.2.0 turns it into a connector for tix: the tracker owns the statuses and the
gates, the agent works with the tracker itself, the daemon only finds tagged tasks in the watched
statuses, runs agents and says when something went wrong.

## Expected result

- `tiny-symphony run` against tix runs `agent:<name>` tasks from the statuses in `watch`.
- The agent takes the task, writes its notes, opens the PR and puts the link into `external`; the
  daemon writes nothing on success.
- The daemon writes only a note plus blocked (agent gave up) or open (PR did not land).
- A central config and an optional project config in the repo, like a user and a project
  `CLAUDE.md`.
- PR watch and cleanup are modules with an on and off switch.

## Philosophy

1. **One job.** Find tagged tasks in the watched statuses, run an agent on each in its own worktree,
   report failures. Not a tracker, not a pipeline, not a merge bot.
2. **Each system owns its state.** Task and status: tracker. Branch: git. PR, CI, merge: GitHub.
   The daemon keeps nothing durable except the attempts file in the worktree.
3. **The agent works like a person.** Same CLI, same rules file, same tracker commands as an
   interactive session. The daemon adds only the worktree and a short prompt.
4. **Humans gate in the tracker.** A gate is a status the daemon does not watch.
5. **Modules are independent and can be turned off.** Dispatch is the core; the rest are switches.
6. **Small and boring.** One binary, stdlib first, no database, no HTTP.

## Tracker interface

One Go interface, one adapter per tracker. 0.2.0 ships tix only.

| Method | tix command | Used by |
| --- | --- | --- |
| `List(statuses)` | `tix list --status <s> --json` | dispatch, watch |
| `Get(id)` | `tix show <id> --json` | before a run, after a run, reconcile |
| `RepoPath(project)` | `tix projects` | dispatch: the project's repository comes from the tracker |
| `Note(id, text)` | `tix note <id> --as <actor> -- <text>` | failures |
| `Move(id, status, reason)` | `tix move <id> <status> -m <reason>` | blocked after `max_attempts`, open after a failed PR |
| `Release(id)` | `tix take <id> --release --as <actor>` | a run ended with the claim still held |

Task fields the daemon reads: `id`, `title`, `project`, `status`, `tags`, `claim`, `external`,
`rank`, `created`. tix has no task dependencies; an epic tag is skipped. Statuses are compared trimmed and lowercased. With
tix 0.9 statuses are names with a kind (idea, open, in_progress, blocked, closed); the daemon takes
names from its config and needs the kind only to find closed tasks for the watch.

## Run

1. **Collect.** Tasks in the `watch` statuses with a tag `agent:<name>` for a known agent, no live
   claim of another actor, not tagged `epic`, a project with a repository. Order: rank, then
   oldest, then id.
2. **Dispatch** while fewer than `max_agents` runs go and the task is not running or in backoff.
3. **Worktree** on `T-<N>-<slug>` from the project repo, found by id and reused across runs.
4. **Agent** in the worktree, own process group, log in `.tiny-symphony/`, env
   `TIX_ACTOR=tiny-symphony:<agent>`, prompt from the layered template (Config).
5. **Outcome.** After exit the daemon re-reads the task:

| Case | Outcome |
| --- | --- |
| exit 0, task left the watched statuses, claim released | success, attempts reset |
| exit not 0, killed, or `run_timeout` | failed attempt |
| exit 0, task still in a watched status, or our claim still held | failed attempt, claim released |
| tag removed, or a claim of another actor | run stopped at the next tick, no attempt |

Failed attempts retry after 1, 5 and 15 minutes with the reason in the prompt. After
`max_attempts` the daemon writes a note with the reason and the log path and moves the task to
`blocked_status`. Attempts live in `.tiny-symphony/attempts` in the worktree, as in 0.1.0.

## Prompt

One template for every status, strict (`text/template`, `missingkey=error`). Variables: `id`,
`title`, `branch`, `worktree`, `attempt`, `last_error`. The built-in text says: take the task with
`tix take`, read it with `tix show`, work only in this worktree, put the PR link into `external`,
hand over by the tracker rules. Everything else comes from the agent's own rules files. The task
text is not copied into the prompt: the agent reads it from the tracker, so it always sees the
latest version and the human's comments.

## Config

Two layers. The project layer wins key by key; tables merge.

1. Central: `~/.config/tiny-symphony/config.toml`.
2. Project, optional: `.tiny-symphony.toml` in the root of the project repository, read from the
   base branch at the start of each run.

```toml
tracker = "tix"
workspace_root = "~/.local/share/tiny-symphony/work"
watch = ["open"]              # statuses where agents pick work up
blocked_status = "blocked"    # where the daemon moves a task after max_attempts
reopen_status = "open"        # where the watch moves a task whose PR did not land
poll_seconds = 30
max_agents = 2
run_timeout_minutes = 60
max_attempts = 3
prompt_append = ""            # text added after the built-in prompt; the project layer adds its own

[agents.claude]
cmd = ["claude", "-p", "--permission-mode", "auto", "{prompt}"]
[agents.codex]                # the sandbox must let the agent write the tracker store
cmd = ["codex", "exec", "--sandbox", "workspace-write", "--add-dir", "~/tasks", "{prompt}"]

[watch_pr]
enabled = false

[cleanup]
enabled = true
log_days = 14
```

The project layer may set `prompt_append`, `[agents.*]`, `max_attempts`, `run_timeout_minutes`.
It may not set `tracker`, `workspace_root` or `watch`: those are one per daemon. `check` prints
the merged config of every project it knows.

## Modules

| Module | What | Switch |
| --- | --- | --- |
| dispatch | Collect, dispatch, outcome, retries, stop, lock | always on |
| PR watch | for each closed task that still has a worktree and a PR link in `external`: `gh pr view --json state,mergedAt,mergeStateStatus,statusCheckRollup`. Merged: note "merged <sha>". CI red or `DIRTY`: note with the reason, move to `reopen_status`. Closed unmerged: note, nothing else | `[watch_pr] enabled` |
| cleanup | closed task, PR merged or no PR: remove the worktree, `git branch -d`; logs older than `log_days` | `[cleanup] enabled` |
| check | config, tracker, agents on PATH, repos, `gh` when the watch is on | command |

The watch never switches auto-merge on and never merges (`docs/process.md`, Merge). A task leaves
the watch when its worktree is removed, so the list stays short.

## Boundaries

- R1 an agent starts only inside `workspace_root`, cwd is the task's worktree.
- R2 a task without an `agent:<name>` tag is never touched.
- R5 no shell between the daemon and the agent.
- R6 one daemon per `workspace_root`.
- R7 no merge, no push, no deletion of an unmerged branch.
- R8 tracker writes of the daemon are only `Note`, `Move` to `blocked_status` or `reopen_status`,
  and `Release` of its own claim.

R3 and R4 of 0.1.0 (pipeline transitions, checked result) go away with the result file.

## What goes away from 0.1.0

The pipeline table and `checkResult`; `result.json` and the agent contract; three prompts by status;
the Backlog.md adapter; `[projects]` in the config (the tracker knows the repository); the Review
checks of S6 (clean tree, pushed branch, PR, `verify`): the agent runs the project checks, CI and
the human review do the rest.

## Decisions

- D4 The agent writes the tracker itself. Was D3 (the daemon is the only writer). Reason: the owner,
  12.11: «это чуть ли не основная фича tix что агент сам работает с трекером». Cost: a sandboxed
  agent needs write access to the tracker store (`--add-dir ~/tasks` for codex).
- D5 The tracker is an interface; tix is the first adapter. Backlog.md is dropped (open question
  Q3).
- D6 Success is read from the tracker, not from a result file: the task left the watched statuses.

## Acceptance

1. A tix task with `agent:claude` in `open` goes through a run to blocked with a PR link in
   `external`, the daemon writing nothing (integration test with a real `tix` binary and a fake
   agent; one live run).
2. An agent that exits 0 without moving the task is a failed attempt; after `max_attempts` the task
   is blocked with a note from the daemon.
3. A project `.tiny-symphony.toml` overrides the agent command and adds to the prompt; `check`
   shows the merged config.
4. With the watch on, a closed task with a merged PR gets a note and its worktree removed; with a
   red or conflicting PR it goes back to open with the reason. With the watch off, GitHub is never
   called.
5. `make ci-check` green; R1, R2, R5-R8 each have a test.

## Plan

One PR per slice into `dev`.

1. Tracker interface and the tix adapter (read side); dispatch runs from tix; Backlog.md adapter
   removed.
2. Outcome from the tracker: drop `result.json`, the pipeline and the per-status prompts; one prompt;
   the daemon's `Note`, `Move`, `Release`.
3. Layered config: central and project file, `prompt_append`, `check` prints the merge.
4. Modules: PR watch and the cleanup switch.
5. Docs (README, architecture, process), live run on a real task (T-665), release 0.2.0.
